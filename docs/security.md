## Аутентификация и сессии (10.2)

- Вход только через SSO (`SsoAdapter`). Mock-IdP регистрируется только вне production; `SSO_PROVIDER=mock`
  в production — ошибка старта (`apps/api/src/config.ts`).
- Сессия: случайный идентификатор 256 бит в cookie `__Host-stories_sid` (HttpOnly, Secure, SameSite=Strict),
  в Redis — только его sha256. Idle 30 минут, абсолютный срок 8 часов. Новый идентификатор при каждом входе.
- CSRF: токен из `/auth/me` в заголовке `X-CSRF-Token` на всех изменяющих запросах + проверка `Origin`
  и `Sec-Fetch-Site`.
- Сетевой доступ к админке и admin API — только из внутренней сети/VPN ИДБ и IP allowlist на ingress
  [ИНТЕГРАЦИЯ]. Admin API — отдельный процесс/порт от публичного.

## Веб

- Админка (nginx, `ops/nginx/admin.conf.template`): `default-src 'self'`, без `unsafe-inline`/`unsafe-eval`,
  `img-src`/`media-src` — свой CDN и хост подписанных URL, `frame-ancestors 'none'`, HSTS, nosniff,
  `Referrer-Policy: strict-origin-when-cross-origin`.
- Публичный API: CORS только для доменов сайта ИДБ (`PUBLIC_CORS_ORIGINS`), без cookie. Admin API: CORS только
  для домена админки.

## Изоляция медиа-воркера (10.5)

Образ `media` (`Dockerfile`): non-root, read-only root FS, запись только в tmpfs, `cap_drop: ALL`,
`no-new-privileges`, seccomp по умолчанию, лимиты CPU/памяти/процессов, таймаут 5 минут на файл (SIGKILL
ffmpeg), лимит кадров и длительности. В compose — сеть `media` с `internal: true`: доступны только Redis
и S3. Учётные данные S3 в проде: чтение `quarantine`, запись `media` (образцы политик — `ops/s3/`).

## Аудит и логи (10.9)

- `audit_log` append-only: у роли приложения нет UPDATE/DELETE/TRUNCATE, триггер запрещает изменения всем.
  Каждое изменение в админке пишется в той же транзакции с diff, IP, User-Agent и `request_id`.
- Структурированные JSON-логи с `request_id`. Токены, cookie, presigned URL, коды OIDC маскируются.
- События безопасности — `category=security` в логах и в SIEM через адаптер: вход/выход/ошибки входа, 403,
  CSRF, CTA вне allowlist, отклонённые загрузки (с причиной и sha256), rate limit, роли, allowlist,
  kill switch, публикации и снятия, попытки самосогласования.
- Алерты — `ops/prometheus/alerts.yml`.

## Хранение данных (10.7)

Сервис не хранит ФИО, телефоны, email покупателей, адреса и заказы; `user_id` используется транзиентно
для запроса сегментов и нигде не пишется. Сырые события — 30 дней, агрегаты — 2 года, аудит — 3 года
(процедура DBA), оригиналы в карантине — 7 дней (lifecycle).
**Запуск таргетинга (фаза 6) — только после согласования с юристом и ИБ ИДБ.**

# Runbook: инцидент с контентом

Признаки: в ленте фишинговая или недопустимая сторис, жалобы, алерт `StoriesPublicationOutsideBusinessHours`,
`StoriesFourEyesViolationAttempt`, подозрение на компрометацию аккаунта сотрудника.

1. **Остановить показ (≤ 1 минуты).**
   - Одна группа: админка → группа → «Снять с публикации» (публикатор или администратор).
   - Непонятен масштаб: админка → Настройки → kill switch → ввести `ОТКЛЮЧИТЬ`. Лента станет пустой
     сразу в API (новое поколение кеша) и не позже чем через 60 секунд на CDN (purge + TTL ≤ 60 с).
   - Без доступа к админке: `UPDATE setting SET value='false' WHERE key='feed_enabled';` владельцем БД,
     затем `redis-cli DEL stories:settings:feed_enabled` и `redis-cli INCR stories:feed:gen` —
     API применит сразу, CDN — не позже чем через 60 секунд.
2. **Отозвать доступ.** Администратор: Пользователи → заблокировать подозрительные учётные записи (все их
   сессии удаляются сразу). Попросить ИБ заблокировать учётку в корпоративном IdP и сбросить MFA.
3. **Собрать данные.** Журнал аудита (фильтр по группе и пользователю), security-логи по `request_id`,
   IP и User-Agent из аудита, версии группы (`/admin/v1/groups/:id/versions`), sha256 медиа.
4. **Медиа.** Опубликованные файлы остаются в `public` по непредсказуемым ключам. При необходимости удалить
   объекты `public/<storageKey>/*` и сделать purge CDN по этим путям [ИНТЕГРАЦИЯ].
5. **Проверить allowlist** (Настройки): не расширял ли его кто-то; изменения видны в аудите и алерте
   `StoriesAllowlistOrRolesChanged`.
6. **Восстановить.** Исправленная версия проходит обычное согласование другим публикатором; kill switch
   включается вводом `ВКЛЮЧИТЬ`.
7. **Разбор.** Отчёт ИБ ИДБ, при утечке персональных данных — по процедуре 152-ФЗ.

# Runbook: подозрительный медиафайл

1. Алерт `StoriesMediaRejectionsPerUser` или событие `media.rejected`: найти пользователя, причины и sha256.
2. Оригинал лежит в `quarantine/uploads/<assetId>` до 7 дней — передать ИБ для анализа, не открывать локально.
3. Если есть признаки RCE в воркере: остановить `media-worker`, пересоздать контейнер из чистого образа,
   сменить ключи S3 воркера и пароль Redis, проверить объекты `media`, созданные после инцидента.

# Бэкапы (раздел 11)

PostgreSQL — ежедневно, хранение 14 дней [ИНТЕГРАЦИЯ с инфраструктурой ИДБ]. Проверка восстановления:
поднять БД из бэкапа, `pnpm db:migrate` (миграции идемпотентны), `pnpm smoke` против стенда.
Redis — только кеш и очереди, восстановления не требует. S3 `public`/`media` — версионирование бакетов
на стороне хранилища.
