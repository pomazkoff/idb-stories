## 1. Цель и границы

**Цель:** ИДБ сама управляет лентой сторис в мобильном приложении (iOS, Android) и на сайте. Маркетинг создаёт и публикует сторис без релизов приложений, продукт видит, как сторис влияют на конверсию.

**Входит в объём (делаем в этом репозитории):**
- Backend: публичный API ленты, admin API, приём событий.
- Админка для маркетинга: редактор, превью, согласование, публикация, статистика.
- Медиа-пайплайн: загрузка, проверка, транскодинг, раздача через CDN.
- Веб-плеер: для превью в админке и для встраивания на сайт.
- Контракт и требования к нативным плеерам (раздел 8) — документ для мобильных команд.
- Безопасность, аудит, мониторинг.

**Не входит в объём:**
- Нативные плееры iOS и Android. Их делают мобильные команды по разделу 8.
- Каталог, цены, остатки. Берутся из систем ИДБ `[ИНТЕГРАЦИЯ]`.
- Авторизация покупателей. Используется существующая `[ИНТЕГРАЦИЯ]`.
- Интерактивные слайды (опросы, квизы) — следующая версия, но модель данных должна позволять их добавить.

## 2. Роли

| Роль | Права |
|---|---|
| Покупатель | Видит опубликованную ленту, генерирует события |
| Редактор | Создаёт и редактирует черновики, загружает медиа, отправляет на согласование |
| Публикатор | Согласует или отклоняет, публикует, снимает с публикации. Не может согласовать собственную правку |
| Аналитик | Только чтение: сторис и статистика |
| Администратор | Пользователи и роли, allowlist ссылок, глобальные настройки, kill switch |

Одному пользователю можно выдать несколько ролей, но правило «четырёх глаз» (раздел 10.3) действует всегда.

## 3. Архитектура

```
[Админка (SPA)] ──SSO──> [Admin API] ─┐
                                      ├─> [PostgreSQL]
[Приложения/сайт] ──> [CDN] ──> [Public API: /feed, /events] ─> [Redis: кеш, rate limit]
                         │                      │
                         └──> [S3 public bucket] │──> [Адаптер аналитики ИДБ]
                                                 │──> [Адаптер авторизации/сегментов ИДБ]
[Загрузка медиа] ──> [S3 quarantine bucket] ──> [Media worker (ffmpeg/libvips, изолирован)] ──> [S3 public bucket]
```

### 3.1 Стек по умолчанию

Если стек ИДБ отличается, это открытый вопрос (раздел 15). До ответа работаем на этом стеке.

- **Язык:** TypeScript (strict), Node.js 22 LTS.
- **API:** Fastify, валидация через zod и общие схемы, OpenAPI 3.1 генерируется из схем.
- **БД:** PostgreSQL 16, Prisma (миграции в репозитории).
- **Кеш, очереди, rate limit:** Redis 7, очереди на BullMQ.
- **Хранилище:** S3-совместимое. Локально MinIO, в проде хранилище в РФ-контуре `[ИНТЕГРАЦИЯ]`.
- **Медиа-воркер:** отдельный контейнер с ffmpeg и libvips (через sharp).
- **Админка:** React, Vite, TypeScript.
- **Веб-плеер:** отдельный пакет на чистом TypeScript без фреймворка, чтобы встраивался куда угодно.
- **Монорепозиторий:** pnpm workspaces.

```
apps/
  api/          # public + admin API (разные префиксы, разные middleware)
  worker/       # медиа-воркер и фоновые задачи
  admin/        # SPA админки
packages/
  schema/       # zod-схемы, типы, экспорт JSON Schema и OpenAPI — единый источник правды
  web-player/   # веб-плеер
  adapters/     # интерфейсы и mock-реализации интеграций ИДБ
docs/
  player-contract.md   # раздел 8, для мобильных команд
  analytics-events.md  # раздел 9
  security.md          # раздел 10 + runbook
```

- **Локальный запуск:** `docker compose up` поднимает всё, включая MinIO, Postgres, Redis и seed-данные.

## 4. Модель данных

### 4.1 Сущности

**StoryGroup** — кружок в ленте:
- `id` (uuid)
- `title` (≤ 40 символов, plain text)
- `cover_asset_id`
- `placement` (enum: `home`, `catalog`, `product`, `cart` — список уточняется)
- `priority` (int, больше — выше)
- `start_at`, `end_at` (UTC, обязательные)
- `platforms` (подмножество `ios | android | web`)
- `min_app_version` (semver, отдельно для iOS и Android, nullable)
- `segment_ids` (массив; пустой — показывать всем)
- `status` (раздел 4.2)
- `created_by`, `updated_by`, временные метки

**Slide:**
- `id`, `group_id`, `position`
- `type` (`image | video | product`; enum расширяемый)
- `duration_ms` (для image и product: 3000–15000, по умолчанию 6000; для video берётся из файла, ≤ 60 000)
- `media_asset_id` (nullable для product)
- `elements` (JSONB, валидируется zod-схемой по типу): текстовые блоки и кнопка CTA
- `product_skus` (для типа product: 1–6 SKU)

**CTA:**
- `type`: `deeplink | product | category | url`
- `value`: диплинк, SKU, ID категории или URL
- `label` (≤ 24 символов)
- Все значения проходят проверку по allowlist (раздел 10.4).

**MediaAsset:**
- `id`, `kind` (`image | video`)
- `status` (`uploaded | processing | ready | rejected`)
- `reject_reason`
- `original_key` (в quarantine)
- `variants` (JSON: ключи в public bucket, размеры, битрейты)
- `sha256`, `size`, `width`, `height`, `duration_ms`, `uploaded_by`

**PublishedSnapshot:** неизменяемый снимок группы со слайдами на момент одобрения. Поля: `group_id`, `version` (int), `payload` (JSONB в формате публичного API), `approved_by`, `approved_at`, `published_at`.

**Лента отдаётся только из снимков, не из редактируемых таблиц.** Благодаря этому покупатели видят ровно то, что согласовано.

**Segment:** справочник, синхронизируется из ИДБ `[ИНТЕГРАЦИЯ]`. Поля: `id` (непрозрачный), `name` (виден только в админке).

**AdminUser, Role, UserRole.**

**AuditLog:** append-only. Поля: `id`, `ts`, `actor_id`, `action`, `entity_type`, `entity_id`, `diff` (до и после), `ip`, `user_agent`, `request_id`.

**Setting:** глобальные настройки, включая `feed_enabled` (kill switch) и allowlist.

### 4.2 Жизненный цикл группы

```
draft → in_review → approved → published → archived
          ↓  ↑
       rejected (→ draft)
```

- `approved → published` происходит автоматически при наступлении `start_at` или вручную.
- `published → archived` происходит автоматически после `end_at` или вручную (снятие с публикации).
- Любая правка опубликованной группы создаёт новый черновик-версию. Старый снимок продолжает показываться, пока новый не пройдёт согласование.

## 5. Публичный API

Базовый префикс: `/v1`. Только HTTPS.

### 5.1 `GET /v1/feed`

**Заголовки:**
- `Authorization: Bearer <токен ИДБ>` — опционально. Без токена отдаётся анонимная лента.
- `X-Platform: ios|android|web` — обязательно.
- `X-App-Version: 5.12.0` — обязательно для iOS и Android.

**Query-параметры:** `placement` (обязательно).

**Логика:**
1. Если `feed_enabled = false`, вернуть `200` с пустым списком `groups`.
2. Взять опубликованные снимки: `start_at ≤ now < end_at`, подходящая платформа, подходящий `min_app_version`, подходящий placement.
3. Если есть валидный токен: получить сегменты пользователя через адаптер `[ИНТЕГРАЦИЯ]` и отфильтровать группы с непустыми `segment_ids`. Если токена нет или адаптер недоступен, отдать только группы без сегментов.
4. Отсортировать: `priority desc`, затем `start_at desc`. Не больше 20 групп и не больше 10 слайдов в группе.

**Пример ответа:**

**Правила ответа:**
- Цены, названия и наличие товаров в ответе не передаются. Клиент получает их из каталога ИДБ по SKU в момент показа. Если товара нет в наличии, клиент скрывает его карточку; если в слайде не осталось товаров, клиент пропускает слайд.
- Имена сегментов, внутренние статусы и авторы в ответе не передаются.
- Все URL медиа указывают только на CDN-домен сервиса.

**Кеширование:**
- Анонимный ответ: `Cache-Control: public, max-age=60`, кешируется на CDN. Ключ кеша: `platform + app_version_bucket + placement`.
- Персонализированный ответ: `Cache-Control: private, no-store`. На сервере кешируется в Redis по ключу `hash(отсортированные segment_ids) + platform + version_bucket + placement`. **Никогда не кешировать по user_id.**
- Снятие с публикации и kill switch сбрасывают кеш Redis и инициируют purge CDN `[ИНТЕГРАЦИЯ]`. Цель — применить изменения меньше чем за 60 секунд.

### 5.2 `POST /v1/events`

- Тело: `{ "events": [ ... ] }`, не больше 50 событий в запросе и не больше 64 КБ.
- Каждое событие валидируется по схеме из раздела 9. Невалидные события отбрасываются, в ответе возвращается счётчик отброшенных.
- Дедупликация по `event_id` (Redis, TTL 24 часа).
- Отправка в аналитику ИДБ через адаптер `[ИНТЕГРАЦИЯ]` с ретраями из очереди.
- Параллельно сервис ведёт собственные агрегаты по дням для статистики в админке: показы, досмотры, CTR на CTA по группам и слайдам.
- Ответ: `202 { "accepted": N, "rejected": M }`.

Если на платформе события уже уходят в аналитику ИДБ напрямую, клиент может не использовать этот эндпоинт. Но для агрегатов в админке нужны как минимум `story_slide_view` и `story_cta_click`. Какую схему выбрать — открытый вопрос №4.

### 5.3 `GET /v1/health`

Liveness и readiness без раскрытия версий зависимостей.

## 6. Admin API и админка

Префикс `/admin/v1`. Отдельный хост или домен от публичного API. Доступ только через SSO (раздел 10.2).

### 6.1 Эндпоинты

- CRUD для групп и слайдов, изменение порядка слайдов, дублирование группы.
- `POST /groups/:id/submit` — отправить на согласование.
- `POST /groups/:id/approve`, `/reject` (с комментарием), `/publish`, `/unpublish`.
- `POST /media/upload-url` — выдаёт presigned PUT в quarantine bucket (TTL 10 минут, фиксированные content-type и лимит размера).
- `POST /media/:id/complete` — ставит задачу на обработку.
- `GET /media/:id`.
- `GET /segments`.
- `GET /stats/groups/:id?from&to`.
- `GET /audit-log` с фильтрами.
- Пользователи и роли.
- Настройки: allowlist, `feed_enabled`.

Каждый эндпоинт проверяет роль на сервере. Проверки только на фронте недостаточно.

### 6.2 Экраны админки

1. **Список групп.** Фильтры по статусу, placement и периоду. Бейджи «идёт сейчас», «запланировано», «истекло».
2. **Редактор группы.** Метаданные, таргетинг, слайды с drag-n-drop, загрузка медиа с прогрессом и статусом обработки, выбор CTA только из допустимых типов, живое превью в веб-плеере в рамке телефона.
3. **Очередь согласования.** Diff с предыдущей опубликованной версией, превью, кнопки «Одобрить» и «Отклонить с комментарием».
4. **Статистика группы.** Показы кружка, открытия, досмотр по слайдам (воронка), клики по CTA, добавления в корзину по атрибуции.
5. **Журнал аудита.**
6. **Настройки:** allowlist, kill switch с подтверждением повторным вводом слова.

Язык интерфейса — русский. Все тексты в интерфейсе хранятся в одном файле локализации.

## 7. Медиа-пайплайн

1. Клиент админки запрашивает presigned URL и загружает файл в **quarantine bucket**. Этот bucket закрыт, доступ к нему есть только у воркера.
2. `complete` ставит задачу в очередь. Воркер:
   - Проверяет размер: изображение ≤ 15 МБ, видео ≤ 200 МБ.
   - Определяет тип **по сигнатуре (magic bytes)**, а не по расширению или Content-Type. Разрешены: JPEG, PNG, WebP, MP4, MOV. Запрещены SVG, GIF, HEIC и всё остальное.
   - Проверяет параметры: изображение от 720×1280 до 4096×4096; видео ≤ 60 секунд, ≤ 60 fps, разрешение ≤ 4K.
   - **Всегда перекодирует.** Изображения в WebP и JPEG-фолбэк, размеры 1080×1920 и 720×1280 (для обложки 256×256). Видео в H.264/AAC MP4, варианты 1080p (~2500 kbps) и 720p (~1200 kbps), плюс постер. Метаданные (EXIF, GPS) удаляются.
   - Записывает результат в **public bucket** под непредсказуемым ключом (content hash + случайная соль).
   - Ставит статус `ready` или `rejected` с понятной причиной.
3. Оригиналы в quarantine удаляются через 7 дней.
4. Медиа черновиков до публикации доступны в админке только по подписанным URL с TTL 15 минут. В публичный CDN-путь медиа попадают только при публикации, чтобы до запуска нельзя было подсмотреть промо.

Требования к изоляции воркера описаны в разделе 10.5.

## 8. Контракт для плееров (web, iOS, Android)

Выносится в `docs/player-contract.md` для мобильных команд. Веб-плеер в этом репозитории — эталонная реализация.

**Лента:**
- Горизонтальный ряд кружков. Просмотренные группы визуально приглушены и сдвигаются в конец ряда.
- Если сервис недоступен или вернул пустой ответ, блок ленты скрывается. Приложение не падает и не показывает ошибку.
- Последний успешный ответ кешируется до `ttl_sec`.

**Плеер:**
- Полноэкранный. Прогресс-бар из сегментов по числу слайдов.
- Тап справа — следующий слайд, тап слева — предыдущий. Удержание — пауза. Свайп вниз — закрыть. Свайп влево или вправо — соседняя группа.
- Автопереход по `duration_ms`. Для видео — по окончанию. Если видео буферизуется, таймер останавливается.
- Предзагрузка следующего слайда и обложки следующей группы.
- **Неизвестный `type` или `elements.kind` — слайд или элемент пропускается молча.** Неизвестный `schema_version` выше поддерживаемого — лента скрывается.
- Текст рендерится **только как plain text** нативными средствами. HTML и Markdown не интерпретируются, WebView для текста не используется.
- Медиа загружаются только с CDN-домена из конфигурации приложения. URL с других хостов игнорируются.
- CTA перед переходом ещё раз проверяется по allowlist на клиенте: схема диплинка и домены (раздел 10.4). К диплинку добавляется параметр атрибуции `story_ref=<group_id>:<slide_id>`.
- Слайд с товарами: запрос в каталог ИДБ по SKU, карточки с ценой и кнопкой «В корзину». Товары, которых нет в наличии, скрываются.
- Доступность: подписи для скринридеров (заголовок группы, текст слайда), кнопка закрытия, пауза при включённом reduce motion.
- Состояние «просмотрено» в MVP хранится локально на устройстве: `group_id + version`. Новая версия группы снова считается непросмотренной.

## 9. Схема аналитических событий

Выносится в `docs/analytics-events.md`. Схемы событий — в `packages/schema`.

**Общие поля каждого события:**

| Поле | Тип | Описание |
|---|---|---|
| `event_id` | uuid v4 | Для дедупликации |
| `event` | string | Имя события |
| `ts` | ISO 8601 | Время на клиенте |
| `session_id` | string | Сессия приложения |
| `platform` | enum | ios, android, web |
| `app_version` | string | |
| `placement` | enum | |
| `group_id`, `group_version` | | Где применимо |
| `slide_id`, `slide_index`, `slide_type` | | Где применимо |

Идентификатор пользователя в события сервиса **не передаётся**. Связь с пользователем, если она нужна, делает система аналитики ИДБ своими средствами.

**События:**

| Событие | Когда | Доп. поля |

## 10. Безопасность

### 10.1 Модель угроз

| # | Угроза | Последствие | Меры |
|---|---|---|---|
| T1 | Скомпрометирован аккаунт редактора, в ленту попадает фишинговая сторис | Кража данных клиентов, репутационный ущерб | SSO + MFA (10.2), правило четырёх глаз (10.3), allowlist CTA (10.4), аудит, kill switch (10.8) |
| T2 | Вредоносный медиафайл (эксплойт парсера ffmpeg или libvips, polyglot-файл) | RCE на воркере, доступ к хранилищу | Карантин, проверка по сигнатуре, обязательное перекодирование, изолированный воркер без сети (10.5) |
| T3 | XSS через текстовые поля (в админке, на сайте, в веб-плеере) | Кража сессии админа или покупателя | Только plain text, экранирование, строгий CSP, запрет `innerHTML` и `dangerouslySetInnerHTML` |
| T4 | Open redirect или фишинг через CTA | Переход на поддельный сайт от имени ИДБ | Allowlist схем и доменов на сервере при сохранении и публикации, и повторно на клиенте |
| T5 | Утечка неанонсированных промо до старта | Коммерческий ущерб | Черновые медиа по подписанным URL, непредсказуемые ключи, группы не отдаются до `start_at` |
| T6 | Утечка признаков таргетинга (сегмент раскрывает чувствительный признак) | Нарушение приватности, 152-ФЗ | Непрозрачные ID сегментов, имена только в админке, персональные ответы с `Cache-Control: private` |
| T7 | Обход авторизации в админке (IDOR, эскалация роли) | Несанкционированная публикация | Проверка прав на каждом эндпоинте на сервере, тесты на каждую пару роль × действие |
| T8 | Флуд или подделка событий | Искажение аналитики, нагрузка | Rate limit, лимиты батча, валидация схемы, дедупликация. Данные событий не используются для решений о деньгах |
| T9 | DoS на `/feed` | Недоступность ленты | CDN, кеш Redis, rate limit, graceful degradation на клиенте |
| T10 | Компрометация зависимостей (supply chain) | Внедрение кода | Lockfile, сканирование зависимостей и образов в CI, закреплённые версии, минимальные базовые образы |
| T11 | Утечка секретов | Доступ к хранилищу или БД | Секреты только из secret manager или env, gitleaks в CI, короткоживущие ключи, отдельные ключи на окружение |
| T12 | Ошибка в токене покупателя (подделка, чужой токен) | Показ чужой персональной ленты | Проверка подписи, срока и audience токена через адаптер. Сервис не хранит токены |

### 10.2 Аутентификация и сессии

- **Админка:** только через корпоративный SSO (OIDC) `[ИНТЕГРАЦИЯ]`, MFA на стороне IdP. Локальных паролей нет. В dev-режиме — mock-IdP, который **невозможно включить** в production (проверка при старте).
- **Сессия админки:** cookie с флагами `HttpOnly`, `Secure`, `SameSite=Strict`. Idle-timeout 30 минут, абсолютный — 8 часов. CSRF-токен на всех изменяющих запросах.
- **Сетевой доступ:** админка и admin API доступны только из внутренней сети или VPN ИДБ `[ИНТЕГРАЦИЯ]`. Дополнительно — IP allowlist на уровне ingress.
- **Токены покупателей:** проверяются адаптером (JWKS или introspection — открытый вопрос №2). Токены не логируются и не сохраняются. Результат (сегменты) кешируется максимум на 5 минут по `sha256(user_id + соль)`.

### 10.3 Правило четырёх глаз и RBAC

- Публикация возможна только после одобрения пользователем с ролью «Публикатор», который **не является автором последней правки** группы. Проверяется на сервере.
- Любое изменение после одобрения сбрасывает статус в `draft`.
- Изменение allowlist, ролей и kill switch — только роль «Администратор», каждое действие фиксируется в аудите.
- Матрица прав хранится в коде как единая таблица, покрыта тестами на все комбинации.

### 10.4 Allowlist для CTA и ссылок

- Хранится в настройках, меняется только администратором.
- **Разрешённые схемы диплинков:** схема приложения ИДБ (уточняется, открытый вопрос №6).
- **Разрешённые домены для `url`:** домены ИДБ (уточняется). Совпадение проверяется по точному хосту или поддомену после нормализации: punycode, нижний регистр, без userinfo, без IP-адресов. Разрешён только `https`.
- Запрещены `javascript:`, `data:`, `file:`, `intent:` и любые схемы вне allowlist.
- Проверка выполняется при сохранении, при согласовании, при публикации (на случай, если allowlist сузили) и повторно на клиенте.

### 10.5 Изоляция медиа-воркера

- Отдельный контейнер, запуск от non-root, read-only root FS, запись только во временный каталог (tmpfs).
- **Без исходящей сети,** кроме S3-эндпоинта. Никаких загрузок по URL, чтобы исключить SSRF: медиа принимаются только загрузкой файла.
- Лимиты: CPU, память, таймаут на файл (5 минут), лимит на число кадров и разрешение для декодера.
- seccomp и AppArmor-профиль по умолчанию или строже, `no-new-privileges`, сброс Linux capabilities.
- ffmpeg собран или установлен с минимальным набором демуксеров и декодеров (только нужные форматы). Версии закреплены, обновления отслеживаются в CI.
- Учётные данные воркера: чтение из quarantine, запись в public. Больше никаких прав.

### 10.6 Защита веб-частей

- **Админка:** строгий CSP (`default-src 'self'`, без `unsafe-inline` и `unsafe-eval`, `img-src` и `media-src` только свой CDN и хост подписанных URL), `frame-ancestors 'none'`, HSTS, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`.
- **Веб-плеер:** только `textContent` и нативный DOM, без `innerHTML`. Совместим со строгим CSP сайта.
- **CORS публичного API:** только домены сайта ИДБ. CORS admin API — только домен админки.

### 10.7 Персональные данные и 152-ФЗ

- Сервис **не хранит** ФИО, телефоны, email, адреса, историю заказов.
- `user_id` используется только транзиентно для запроса сегментов. В логах и событиях его нет.
- Хранение и обработка — в инфраструктуре на территории РФ `[ИНТЕГРАЦИЯ]`.
- Имена сегментов и правила таргетинга могут раскрывать чувствительные признаки. Такие сегменты заводятся только после согласования с юристом и службой информационной безопасности (открытый вопрос №8).
- Сроки хранения: сырые события в сервисе — 30 дней, агрегаты — 2 года, аудит — 3 года (уточняется у ИБ), оригиналы в карантине — 7 дней.
- **Нужна проверка юристом ИДБ до запуска таргетинга (фаза 6).**

### 10.8 Kill switch

- Выключение всей ленты (`feed_enabled = false`) и снятие отдельной группы — одно действие в админке.
- Применяется быстрее чем за 60 секунд: сброс кеша Redis, purge CDN, TTL ответа ≤ 60 секунд.
- В runbook (`docs/security.md`) описан порядок действий при инциденте с контентом.

### 10.9 Аудит, логирование, мониторинг безопасности

- **AuditLog** — append-only: у пользователя БД для приложения нет прав `UPDATE` и `DELETE` на эту таблицу. Пишутся все изменяющие действия в админке с diff.
- **Структурированные логи** (JSON) с `request_id`. Токены, cookie, presigned URL и тела запросов с пользовательскими данными не логируются (маскирование в логгере, покрыто тестом).
- **События безопасности** пишутся отдельной категорией логов для отправки в SIEM `[ИНТЕГРАЦИЯ]`:
  - вход и выход, неуспешная аутентификация;
  - отказ в доступе (403);
  - попытка сохранить CTA вне allowlist;
  - отклонённая загрузка медиа (с причиной и sha256);
  - превышение rate limit;
  - изменение ролей, allowlist, kill switch;
  - публикация и снятие с публикации;
  - попытка самосогласования.
- **Алерты** (Prometheus-метрики плюс правила):
  - всплеск 401/403 в admin API;
  - больше N отклонённых загрузок за час от одного пользователя;
  - любое изменение allowlist или ролей;
  - публикация вне рабочего времени;
  - ошибки адаптера авторизации;
  - доля 5xx на `/feed`.

### 10.10 Безопасная разработка (CI)

Обязательные шаги в CI; каждый ломает сборку при находках уровня high и выше:
- lint и typecheck;
- unit- и интеграционные тесты;
- `pnpm audit` или osv-scanner по зависимостям;
- semgrep (SAST) с правилами для TypeScript и React;
- gitleaks (секреты);
- trivy (сканирование Docker-образов);
- проверка, что OpenAPI сгенерирован и закоммичен.

Также: Renovate или Dependabot для обновлений, базовые образы distroless или slim с закреплённым digest.

### 10.11 Приёмка по безопасности

Автотесты, которые должны быть написаны и проходить:
- Каждая пара роль × эндпоинт admin API возвращает ожидаемый 200 или 403.
- Автор правки не может её одобрить.
- CTA с `javascript:`, `data:`, чужим доменом, IP-адресом, userinfo (`https://iledebeaute.ru@evil.com`), punycode-двойником отклоняется.
- Загрузка SVG, HTML, polyglot JPEG+HTML, файла с подменённым расширением, файла-бомбы по разрешению отклоняется.
- Текст с `<script>`, `<img onerror>` отображается в плеере и админке как текст.
- Группа до `start_at` и после `end_at` не попадает в `/feed`. Медиа черновика недоступно без подписи.
- Персональный ответ `/feed` содержит `Cache-Control: private`.
- Логи не содержат токенов и cookie (тест на логгер).
- Rate limit срабатывает на `/events` и `/feed`.
- Kill switch опустошает ленту в пределах TTL.

## 11. Нефункциональные требования

- **`/feed`:** p95 < 150 мс при попадании в кеш, < 400 мс без кеша. Размер ответа < 100 КБ.
- **Нагрузка:** рассчитываем на 500 RPS на `/feed` на одном инстансе за CDN (проверка через k6, сценарий в репозитории). Реальные цифры уточняются (открытый вопрос №9).
- **Масштабирование:** API без состояния, масштабируется горизонтально.
- **Доступность:** 99.9% для `/feed`. При недоступности сервиса клиенты скрывают ленту.
- **Бэкапы:** БД ежедневно, хранение 14 дней. Процедура восстановления описана и проверена.
- **Наблюдаемость:** метрики Prometheus, health-чеки, трассировка через `request_id`.

## 14. Критерии приёмки MVP (фазы 0–5)

1. Редактор создаёт группу из изображений и видео с CTA за ≤ 5 минут без помощи разработчика.
2. Публикация возможна только после согласования другим человеком.
3. Лента отображается в веб-плеере и отдаётся по контракту для мобильных плееров.
4. Снятие с публикации и kill switch применяются менее чем за 60 секунд.
5. В админке видна воронка по слайдам и CTR на CTA.
6. Все проверки безопасности из 10.11 проходят. CI без находок уровня high.

## 15. Открытые вопросы

Решает ИДБ. До ответа Claude Code использует mock и фиксирует допущения в `DECISIONS.md`.

1. Стек и хостинг ИДБ: язык и фреймворк бэкенда, Kubernetes или VM, S3-хранилище, CDN, где будет жить сервис.
2. Формат токена покупателя и способ проверки (JWT + JWKS или introspection), audience и issuer.
3. IdP для SSO сотрудников (OIDC или SAML), группы для маппинга ролей.
4. Система аналитики ИДБ: как принимает события, нужен ли проксирующий `/events` или клиенты шлют напрямую; модель и окно атрибуции покупок.
5. Источник сегментов, формат и частота синхронизации.
6. Схема диплинков приложения и список разрешённых доменов.
7. Список placements: где в приложении и на сайте будет лента.
8. Согласование таргетинга с юристом и ИБ: какие сегменты допустимы.
9. Ожидаемая нагрузка: DAU приложения, пиковый RPS.
10. SIEM ИДБ и формат отправки событий безопасности.
11. Сроки хранения аудита и событий по требованиям ИБ.
12. Требования ИБ ИДБ к пентесту перед запуском.
